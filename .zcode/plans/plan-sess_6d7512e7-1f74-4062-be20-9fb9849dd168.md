## 重构目标
将已迁移的支付后台从“功能可运行”调整为符合 `AGENTS.md` 的三层架构、日志、异常和安全规范，同时保持现有 API 契约、支付协议和 `src/client/**` 不变。

## 1. 目录和职责重构
- 将 `src/worker/controller/**` 重命名/整理到 `src/worker/routes/**`，按业务边界拆分：
  - `routes/gateway.ts`
  - `routes/easypay.ts`
  - `routes/downstream-test.ts`
  - `routes/admin.ts`
  - 保留现有 health/auth/services/settings 路由并统一命名。
- 将 `src/worker/service/**` 调整为 `src/worker/services/**`。
- 将 `src/worker/dao/**` 调整为 `src/worker/repositories/**`，保持 Drizzle/D1 访问只在 Repository 层。
- 将认证共享逻辑从当前 `libs/auth` 整理到规范要求的 `src/worker/auth/**`；避免保留两套认证实现，Controller/Route 不直接实现认证算法。
- `src/worker/index.ts` 只负责中间件、鉴权中间件、路由挂载、统一 `notFound/onError` 和 scheduled 入口，不保留业务流程。

## 2. 请求级依赖和 Service 边界
- 新增请求级依赖工厂或构造函数约定，由 Route 使用 `c.env` 创建 Repository/Service；禁止模块级可变单例和 Service 内隐式持有 Hono Context。
- Service 接收显式依赖和经过校验的 DTO，不读取 `c.req`、不返回 Hono Response、不处理 HTTP 状态码。
- 将订单、支付回调、退款、订单投递、应用/provider 管理、EasyPay 业务流程分别封装在 Service 中。
- 迁移所有 Route 中的数据库查询、更新、时间/状态计算、provider 选择和流程编排到对应 Service/Repository。
- scheduled 流程通过 Service 执行过期和重试，不在入口中直接操作 DAO。

## 3. Controller/Route 输入校验和响应
- 为管理 API、订单/退款、EasyPay 创建/查单/退款、支付通知定义明确 DTO 和校验函数，限制字符串长度、金额精度、枚举、URL 协议和分页范围。
- JSON、form-urlencoded、query、path、header 全部视为不可信输入；解析失败统一转为 `VALIDATION_ERROR`。
- Route 只做：读取请求、校验/规范化、记录摘要日志、调用 Service、映射稳定 JSON/文本/重定向响应。
- 不在 Route 中直接使用 Drizzle、拼 SQL、执行 `new Date()` 业务计算或 `crypto.randomUUID()` 业务建模。
- 保留 EasyPay、Alipay、Wechat Pay、Stripe 回调的协议特定文本/JSON响应，但错误映射集中到 Route 层。

## 4. 统一异常处理
- 保留当前 `HTTPException` 和 `BusinessException` 体系，新增/扩展支付领域错误码和状态码映射。
- Service 对可预期业务失败统一抛出不依赖 Hono 的 `BusinessException`，例如订单不存在、金额不匹配、provider 未配置、订单状态冲突、退款不允许。
- 输入错误由 Route 抛出 `HTTPException`，统一结构为 `{ error: 'VALIDATION_ERROR', message: '请求参数无效', details: {} }`。
- 外部支付 provider 或 D1 未预期失败由入口 `onError` 转为安全 500/502 响应，不向客户端返回 provider 原始 body、数据库错误、密钥或堆栈。
- 统一各路由的 401/404/409/422/502/503 响应格式，同时兼容支付协议要求的 `success/fail`、EasyPay `code/msg` 等外部格式。

## 5. 统一日志和敏感信息处理
- Route 使用当前 `log(controller, phase, requestId, summary)` 格式记录入参/出参；从 `c.get('requestId')` 获取请求 ID。
- 删除支付 Route 中直接 `console.info('[payment] ...')` 的通用 HTTP 日志，避免和 Hono logger 重复。
- 业务 Service 不打印 HTTP 入参/出参日志；如需业务审计，只记录脱敏后的 action、orderId、providerKey、状态和结果代码。
- EasyPay form 参数日志只记录字段存在性、长度、金额是否有效、paymentType、redirect 等摘要，不记录 `key`、`sign`、`secret`、完整 URL 或完整 body。
- provider/bridge 错误日志只记录稳定错误码和请求 ID，不输出签名、token、密钥、完整支付响应或数据库敏感字段。
- 确保 `BusinessException` 与 `onError` 日志遵循当前 `[requestId][...]` 格式。

## 6. 入口和认证规范
- 调整 `src/worker/index.ts` 注册顺序为：requestId、logger、CORS/安全头、认证/权限中间件、业务路由、notFound、onError。
- 所有业务 API 继续挂载在 `/api` 下；导航回调保留 `/auth/callback`，成功后清理 URL 中 token 并重定向到当前 UI `/`。
- `requireAuth` 和 `requireSessionAuth` 放入统一 `src/worker/auth`/middleware 边界，默认拒绝访问，本地绕过只允许 localhost 和显式环境变量。
- 保持支付通知和 EasyPay 外部入口按协议公开访问，管理 API 默认鉴权。

## 7. 测试策略
- 保留当前支付 provider 单元测试，并调整 import 路径。
- 新增/扩展真实 Hono `SELF.fetch` API 测试，覆盖：
  - 管理 API 未认证、合法请求、JSON/form/query/path 校验失败
  - 未知应用、订单、provider、退款状态冲突
  - EasyPay 签名失败、金额/URL/订单号非法、查单和退款
  - 支付通知无配置、签名失败、订单不存在、金额不匹配、重复通知
  - request ID 响应头与日志摘要行为
  - 现有 `/api/services`、`/api/settings`、TOTP/session/API token 回归
- 对 Service 重点测试业务异常类型和状态，不依赖 Hono Context。

## 8. 验证顺序
- 先做目录/导入重构和依赖注入，运行 `npm run build` 修复类型边界。
- 再做异常和日志统一，运行 `npm test`。
- 最后运行 `npm run format:check`、`npm run build`、`npm test`、`npm run check`，并确认 `src/client/**` 无变更。
- 对真实支付 provider 和远端 D1 仅做本地 mock/Worker Pool 验证，不执行生产退款或真实支付操作。
