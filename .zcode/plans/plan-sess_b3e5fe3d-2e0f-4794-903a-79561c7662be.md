## 目标

基于 Hono `HTTPException` 建立统一异常体系，并定义一个与 HTTP 解耦的项目级业务异常，统一可预期错误响应和日志行为。

## 异常分层

1. **HTTP 异常**：使用 Hono 官方 `HTTPException`，只用于 Controller/认证中间件等 HTTP 边界场景，例如未认证、参数格式错误、资源不存在。
2. **业务异常**：新增项目级 `BusinessException`，位于 `src/worker/errors/`，不依赖 Hono；包含稳定的业务错误码、用户安全消息和可选 HTTP 状态码/详情，由入口错误边界统一转换为 JSON。
3. **未预期异常**：普通 `Error` 或未知异常统一由 `app.onError()` 记录安全日志并返回 `500 INTERNAL_SERVER_ERROR`，不泄露堆栈、数据库错误或敏感信息。

## 建议的统一异常类型

- `AppException`：项目异常基类，包含 `code`、`message`、`status` 和可选 `details`。
- `BusinessException extends AppException`：业务规则失败，例如设置值非法、资源状态不允许、业务对象不存在。
- `HTTPException`：继续使用 Hono 官方类，不自定义重复实现；通过 `getResponse()` 保留状态码和响应体能力。
- 可选的固定工厂/子类：`BadRequestException`、`UnauthorizedException`、`NotFoundException`，仅在重复场景明显时增加，避免异常类泛滥。

## 实施步骤

1. **新增异常模块**
   - 新增 `src/worker/errors/app.ts`：定义 `AppException`、`BusinessException` 和稳定错误码类型。
   - 新增 `src/worker/errors/http.ts`：封装项目常用 `HTTPException` 构造器或工厂，统一响应结构 `{ error, message, details? }`。
   - 保证异常模块只依赖 Web/Hono 标准能力，不读取 `c.env`，不访问数据库。

2. **统一错误边界**
   - 在 `src/worker/index.ts` 的 `app.onError()` 中优先处理 Hono `HTTPException`：直接返回其 `getResponse()` 或转换成项目统一 JSON。
   - 处理 `BusinessException`：使用其 `status`、`code`、安全 `message` 和 `details` 返回 JSON。
   - 未知异常返回 `500`，日志只记录错误类型、错误码、requestId 和安全上下文，不打印 Token、Cookie、TOTP、Secret、完整 Body 或数据库值。
   - `app.notFound()` 统一改为抛出/映射 `NotFoundException` 或直接使用同一错误响应工厂，返回稳定 `{ error: 'NOT_FOUND', message: '资源不存在' }`。

3. **改造 Controller 和中间件**
   - Controller 校验失败改为抛出 `HTTPException(400, ...)` 或统一 `BadRequestException`，不在每个路由重复拼装错误 JSON；仍按现有约定记录 `[xxx][出参]` 日志。
   - `requireAuth` 未认证改为抛出 `HTTPException(401, ...)`，由全局错误边界统一返回；保持原有 `{ error: 'Unauthorized' }` 或明确更新为统一结构并同步测试。
   - Services Controller 查不到资源时抛出 `NotFoundException`，不在路由中内联三元响应。
   - 不把 Hono `HTTPException` 传入 Service；Service 只抛出 `BusinessException` 或领域错误。

4. **接入一个实际业务异常**
   - Settings Service 对已校验 DTO 执行 upsert；Repository 写入后未找到记录时抛出 `BusinessException`，例如 `SETTING_PERSIST_FAILED`，由全局边界转换为 `500` 安全响应。
   - 如要展示更清晰的业务规则，可让 Settings Service 在领域状态不允许时抛出 `BusinessException`；Controller 仍只负责输入校验。
   - 保持现有成功响应、认证行为和 D1 数据结构不变。

5. **测试与验证**
   - 增加异常映射测试：`HTTPException` 的状态/响应、`BusinessException` 的错误码和状态、未知异常的 `500` 安全响应。
   - 更新 API 测试覆盖未认证、非法输入、资源不存在和 Repository/Service 异常，确认响应不泄露内部错误。
   - 验证日志仍使用 `[xxx][入参]` / `[xxx][出参]` 并携带 requestId，异常日志不包含敏感值。
   - 运行 `npm run build`、`npm test`、`npm run check`。

## 交付结果

异常处理链路为：

```text
Controller 校验
  -> HTTPException（HTTP 边界错误）
Service 业务规则
  -> BusinessException（业务错误）
Repository/Adapter
  -> 普通 Error（基础设施故障）
入口 app.onError()
  -> 统一 JSON 响应 + 安全日志
```

这样既遵循 Hono 官方异常机制，又保持 Service/Repository 不依赖 Hono，后续可复用到队列、定时任务或其他非 HTTP 入口。
